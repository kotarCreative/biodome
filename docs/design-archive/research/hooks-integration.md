# Hooks, Customization, and Integration with pi.dev & OpenCode

## Overview

A sandbox manager should provide hooks for customization and integration with AI coding agents. This document covers hook patterns, how pi.dev (Pi Coding Agent) and OpenCode work, and how the sandbox manager can integrate with both.

---

## 1. Hook Architecture Patterns

### Lifecycle Events for Sandbox Hooks

A sandbox manager should expose hooks at key lifecycle points:

| Event          | Phase    | Description                                   |
| -------------- | -------- | --------------------------------------------- |
| `pre-build`    | Build    | Before building the Docker image              |
| `post-build`   | Build    | After image build completes                   |
| `pre-start`    | Run      | Before container starts                       |
| `post-start`   | Run      | After container is ready                      |
| `pre-stop`     | Shutdown | Before stopping the container                 |
| `post-stop`    | Shutdown | After container stops                         |
| `pre-exec`     | Runtime  | Before executing a command inside the sandbox |
| `post-exec`    | Runtime  | After a command completes                     |
| `file-changed` | Runtime  | When tracked files change (via watcher)       |
| `session-idle` | Runtime  | When no activity for a configurable period    |

### Hook Action Types

Hooks should support multiple action types:

```yaml
hooks:
  pre-start:
    - type: command
      command: ./scripts/setup-db.sh
      timeout: 30s
    - type: http
      url: https://hooks.example.com/notify
      method: POST
    - type: exec
      container: db
      command: ["psql", "-f", "/init.sql"]
    - type: inline
      script: |
        echo "Setting up environment..."
        export FOO=bar
```

## 2. pi.dev (Pi Coding Agent) Integration

### About Pi

Pi is a minimal, open-source (MIT) terminal coding agent. It is distributed as an npm package and features four built-in tools: `read`, `write`, `edit`, `bash`. It is intentionally minimal -- no built-in MCP, sub-agents, permission popups, plan mode, or background bash. All these can be added via extensions, skills, and packages.

**Source**: https://pi.dev/docs/latest/usage

### Pi's Architecture

```
Pi instance (runs in terminal)
  |-- Built-in tools: read, write, edit, bash, grep, find, ls
  |-- Extensions (.ts modules adding tools/commands/keybindings)
  |-- Skills (contextual prompt/tool bundles)
  |-- Prompt templates
  |-- Packages (bundled extensions + skills + prompts + themes)
  |-- Context files: AGENTS.md, CLAUDE.md, SYSTEM.md
```

### Integration Points for Sandbox Manager

#### 1. Containerization Support

Pi has explicit documentation for running inside containers:
https://pi.dev/docs/latest/containerization

Key recommendations:

- Pi runs fine inside a Docker container
- The `bash` tool should ideally run inside a sandbox
- Mount the project directory at the same path as the host (for git, absolute paths)

**Sandbox Manager should provide:**

- A Docker image with Pi pre-installed
- Volume mounts that mirror host paths for git compatibility
- Credential mounting (read-only, per-project scoped)

#### 2. Pi Tool Config as Hooks

Pi's `--tools` flag can enable/disable specific tools. The sandbox manager could generate Pi config:

```bash
# Sandbox manager makes Pi available with specified tools
pi --tools read,bash,edit,write,grep,find,ls
```

#### 3. Extensions API

Pi extensions can add custom tools. The sandbox manager could provide a Pi extension for sandbox lifecycle management:

```typescript
// Pi extension for sandbox control
export const extension: Extension = (pi) => {
  pi.command("sandbox:rebuild", async () => {
    await exec("sandbox build");
    pi.message("Sandbox rebuilt");
  });

  pi.command("sandbox:restart-service", async (name) => {
    await exec(`sandbox service restart ${name}`);
  });
};
```

#### 4. Context Files

Pi loads `AGENTS.md` or `CLAUDE.md` at startup. The sandbox manager could generate these:

```markdown
# AGENTS.md (auto-generated by biodome)

## Dev Environment

- Node.js 20, Python 3.12, Go 1.22
- PostgreSQL on port 5432
- Redis on port 6379

## Available Commands

- `npm test` to run tests
- `npm run dev` to start dev server

## Credentials

- DB connection: postgres://user:pass@localhost:5432/mydb
- API keys are in ~/.sandbox/secrets.env
```

**Source**: https://pi.dev/docs/latest/quickstart

#### 5. Pi Packages for Sandbox Environments

Pi packages can bundle extensions, skills, and prompts. The sandbox manager could publish per-environment packages:

```bash
pi install biodome/node-project
pi install biodome/python-ml-project
```

#### 6. Environment Variables

Pi supports `PI_OFFLINE`, `PI_CODING_AGENT_DIR`, etc. The sandbox manager should set appropriate defaults:

- `PI_CODING_AGENT_DIR=~/.sandbox/pi` for isolated config
- `PI_OFFLINE=1` if the sandbox has restricted network access

## 3. OpenCode Integration

### About OpenCode

OpenCode is a terminal-based AI coding agent with a rich plugin system, MCP support, custom commands, and hooks (YAML-based lifecycle hooks). It has a pluggable architecture with TypeScript/JavaScript plugins.

### OpenCode's Hook Systems

OpenCode has **four** hook mechanisms (per documentation):

1. **Plugins** (TypeScript/JS) -- most powerful, can intercept events, modify parameters
2. **`hooks.yaml`** -- YAML-based lifecycle hooks for simpler automation
3. **MCP Servers** -- protocol-based tool integration
4. **Custom Commands** -- markdown-defined reusable prompts

### OpenCode Hooks System (hooks.yaml)

OpenCode supports a YAML-based hooks system that the community maintains:
https://github.com/KristjanPikhof/OpenCode-Hooks

```yaml
hooks:
  - event: tool.before.bash
    action: stop
    actions:
      - command: safety-check.sh
    conditions:
      - matchesAnyPath: scripts/deploy.sh
  - event: file.changed
    actions:
      - command: npm run lint -- --fix
      - command: npm test -- --changed
  - event: session.created
    actions:
      - command: echo "Session started"
  - event: session.idle
    conditions:
      - matchesCodeFiles
    actions:
      - bash: git add -A && git stash
```

Available events:

- `session.created`, `session.deleted`, `session.idle`
- `file.changed`
- `tool.before.*`, `tool.before.<tool_name>`
- `tool.after.*`, `tool.after.<tool_name>`

### OpenCode Plugin System

Plugins extend OpenCode with custom tools, hooks, and integrations:
https://opencode.ai/docs/plugins

```typescript
import type { Plugin } from "@opencode-ai/plugin";

export const SandboxPlugin: Plugin = async (ctx) => {
  return {
    tool: {
      "sandbox:rebuild": {
        name: "sandbox:rebuild",
        description: "Rebuild the sandbox environment",
        parameters: {},
        execute: async () => {
          await ctx.exec("sandbox build");
          return { content: "Sandbox rebuilt" };
        },
      },
      "sandbox:logs": {
        name: "sandbox:logs",
        description: "View sandbox logs",
        parameters: {
          service: { type: "string", optional: true },
        },
        execute: async ({ service }) => {
          const logs = await ctx.exec(`sandbox logs ${service || ""}`);
          return { content: logs.stdout };
        },
      },
    },
    "chat.params": async (input, output) => {
      // Inject sandbox context into LLM params
      output.system =
        (output.system || "") +
        "\n\nYou are running inside a sandbox environment " +
        "with Node.js 20, Python 3.12, and PostgreSQL.";
    },
  };
};
```

### OpenCode Config Integration

OpenCode uses `opencode.json` for configuration with layered precedence:

1. Remote config (`.well-known/opencode`)
2. Global config (`~/.config/opencode/opencode.json`)
3. Custom config (`OPENCODE_CONFIG` env var)
4. Project config (`opencode.json` in project root)

**Sandbox Manager could auto-generate project-level config:**

```json
{
  "$schema": "https://opencode.ai/config.json",
  "instructions": [".sandbox/AGENTS.md"],
  "mcp": {
    "sandbox": {
      "type": "local",
      "command": ["sandbox", "mcp"],
      "enabled": true
    }
  },
  "hooks": {
    "pre-tool-bash": "sandbox check-permissions"
  }
}
```

**Source**: https://opencode.ai/docs/config/

### OpenCode MCP Servers

MCP (Model Context Protocol) servers provide tools to the agent:

```json
{
  "mcp": {
    "sandbox-db": {
      "type": "local",
      "command": ["sandbox", "mcp", "db"],
      "enabled": true
    },
    "sandbox-exec": {
      "type": "local",
      "command": ["sandbox", "mcp", "exec"],
      "enabled": true
    }
  }
}
```

### Integration with Agentrove

Agentrove (https://github.com/Mng-dev-ai/agentrove) is a self-hosted workspace for running multiple AI coding agents. It supports Claude Code, Codex, Copilot, Cursor, and OpenCode through ACP adapters. Each workspace gets its own Docker or host sandbox.

Integration points:

- ACP (Agent Communication Protocol) for agent/framework interop
- Docker sandboxes per workspace
- Web-based IDE + terminal + file tree

## 4. Proposed Sandbox Manager Hook Architecture

### Config-level Hooks

```yaml
# sandbox/config.yaml
name: my-project
image: ghcr.io/biodome/node:20-python:3.12
```

```yaml
# sandbox/env.yaml
packages:
  apt:
    - postgresql-client
    - redis-tools
  npm:
    - typescript
    - vite
```

```yaml
# sandbox/services.yaml
db:
  image: postgres:16-alpine
  ports: ["5432:5432"]
  env:
    POSTGRES_PASSWORD: dev
redis:
  image: redis:7-alpine
  ports: ["6379:6379"]
```

```yaml
# sandbox/hooks.yaml
build:
  pre:
    - command: ./scripts/check-versions.sh
    - inline: echo "Building sandbox for $USER"
  post:
    - command: ./scripts/validate-image.sh

start:
  post:
    - command: ./scripts/wait-for-db.sh
    - command: ./scripts/run-migrations.sh
    - inline: |
        echo "Sandbox ready!"
        echo "PostgreSQL: postgres://user:pass@localhost:5432/mydb"

stop:
  pre:
    - command: ./scripts/backup-data.sh

# Agent integrations
agents:
  opencode:
    config:
      mcp:
        sandbox-db:
          type: local
          command: ["sandbox", "mcp", "db"]
    hooks:
      - event: tool.before.bash
        action: safe-exec

  pi:
    packages:
      - biodome/pi-tools
    context: .sandbox/AGENTS.md
```

### Plugin System

The sandbox manager itself should support plugins:

```typescript
// TypeScript plugin interface (TypeScript)
interface SandboxPlugin {
  name: string;

  hooks: {
    "build.pre"?: (ctx: BuildContext) => Promise<void>;
    "build.post"?: (ctx: BuildContext) => Promise<void>;
    "start.pre"?: (ctx: RunContext) => Promise<void>;
    "start.post"?: (ctx: RunContext) => Promise<void>;
    "stop.pre"?: (ctx: RunContext) => Promise<void>;
    "stop.post"?: (ctx: RunContext) => Promise<void>;
    "exec.pre"?: (ctx: ExecContext) => Promise<boolean>; // return false to block
    "exec.post"?: (ctx: ExecContext) => Promise<void>;
    "tool.install"?: (ctx: ToolContext) => Promise<void>;
    "file.changed"?: (ctx: FileContext) => Promise<void>;
    "session.idle"?: (ctx: IdleContext) => Promise<void>;
  };

  // Custom config keys
  config?: Record<string, ConfigSchema>;

  // Custom tool providers for MCP
  mcp?: Record<string, MCPServerDefinition>;

  // Provider backends (e.g., Docker, Fly.io, Modal)
  provider?: ProviderInterface;
}
```

### Example Plugins

**Docker Build Cache:**

```yaml
# sandbox/config.yaml
build:
  cache:
    registry: ghcr.io/myorg/cache
    mode: max
```

**Idle Management:**

```yaml
# sandbox/config.yaml
idle:
  timeout: 30m
  action: stop # stop, snapshot, or hibernate
```

**GitHub Actions Prebuild:** Handled by `sandbox generate ci`, not sandbox config. The generated workflow triggers on changes to `sandbox/**/*.yaml`.

## 5. Capabilities Matrix: What to Build

### Phase 1: Core Hooks (MVP)

| Hook         | Purpose                           |
| ------------ | --------------------------------- |
| `build.pre`  | Install system dependencies       |
| `build.post` | Verify build succeeded            |
| `start.post` | Wait for services, run migrations |
| `stop.pre`   | Save state, clean up              |
| `stop.post`  | Notify services                   |

These cover the majority of real-world use cases.

### Phase 2: Agent Integration

| Integration      | Mechanism            | Value                               |
| ---------------- | -------------------- | ----------------------------------- |
| OpenCode MCP     | MCP server plugin    | Agent can query/log/control sandbox |
| OpenCode plugin  | Plugin API           | Custom sandbox tools in OpenCode    |
| Pi extension     | Pi extension API     | Custom sandbox commands in Pi       |
| Pi context files | AGENTS.md generation | Autogenerated env docs for agents   |

### Phase 3: Advanced Hooks

| Hook                  | Purpose                                         |
| --------------------- | ----------------------------------------------- |
| `exec.pre`            | Security policy checks before command execution |
| `exec.post`           | Log all commands for audit                      |
| `file.changed`        | Trigger test runs, linting                      |
| `session.idle`        | Auto-stop to save cost                          |
| `agent.session.start` | Notify agent session started                    |
| `agent.session.end`   | Collect agent logs and metrics                  |

### Phase 4: Plugin System

| Feature           | Description                               |
| ----------------- | ----------------------------------------- |
| Lifecycle plugins | Hook into build/start/stop events         |
| Provider plugins  | Add new infrastructure backends           |
| Tool plugins      | Add custom tools installed in the sandbox |
| Config plugins    | Add custom config schema sections         |
