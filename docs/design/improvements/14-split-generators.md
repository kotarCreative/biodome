# Plan 14: Split Docker Generators by Complete Output

Status: proposed. The runtime layout and shared artifact renderer are already in place; this plan is a behavior-preserving organization change on top of them.

## Objective

Replace the 1,300-line `src/docker/generator.ts` module with cohesive modules that each own one complete generated artifact or harness family, without changing generated bytes or runtime behavior.

## Current Architecture

- `src/docker/generator.ts` owns Dockerfile, `.dockerignore`, Compose, supervisor, health-check, repository, and four harness generator families.
- `src/runtime/layout.ts` is the source of truth for target-scoped host and container paths.
- `src/runtime/artifacts.ts` composes common generated files, copies the MCP runtime tree, applies write policies and modes, validates output paths, and writes artifacts.
- `src/runtime/docker-compose.ts` and `src/runtime/docker-sandbox.ts` add backend-specific Compose output to the common artifact manifest.
- `src/runtime/aws-ecs.ts` consumes only the common artifact renderer because it does not produce Compose output.
- `src/mcp/generator.ts` separately owns MCP plan serialization and is outside this split.

## Preconditions

- Preserve the contracts in `src/runtime/layout.ts` and `src/runtime/artifacts.ts`.
- Run the existing generator, artifact, and layout tests before editing to establish a baseline.
- Do not depend on the removed Plan 02 or Plan 06 documents; their layout and shared-rendering work is already present in the current tree.

## Files

- Replace `src/docker/generator.ts` with modules below `src/docker/generators/`.
- Update imports in `src/runtime/artifacts.ts`, `src/runtime/docker-compose.ts`, and `src/runtime/docker-sandbox.ts` to use final module paths.
- Update direct generator imports in `src/tests/builder/index.test.ts`, `src/tests/apps/end-to-end.test.ts`, and `src/tests/integration/docker-build.test.ts`.
- Split `src/tests/docker/generator.test.ts` below `src/tests/docker/generators/` by output family.
- Split or relocate `src/tests/docker/generator.snapshot.test.ts` and its snapshot without accepting changed output.
- Keep `src/tests/runtime/artifacts.test.ts` and `src/tests/runtime/layout.test.ts` in place.

## Locked Decisions

- Split by cohesive generated output, not by arbitrary helper size.
- Keep all generation functions pure and deterministic.
- Preserve the existing exported function names, option types, return types, and default behavior during the split.
- Preserve every generated file path, file mode, write policy, and byte of generated content.
- Keep `runtimeLayout` as the only runtime path model. Extracted modules consume its container fields rather than rebuilding `.biodome-build` paths.
- Keep common artifact composition, MCP runtime copying, path validation, and filesystem writes in `src/runtime/artifacts.ts`.
- Keep Compose generation backend-specific. Compose-capable drivers may import `generateCompose` directly; other runtime drivers must use only the common artifact renderer.
- Keep harness-specific configuration, startup scripts, task scripts, hooks, and telemetry adapters together.
- Share only helpers with multiple real consumers. Do not introduce a generic harness abstraction.
- A temporary `src/docker/generator.ts` re-export barrel is allowed while imports migrate, but remove it before completing the plan.

## Target Modules

| Module                                        | Ownership                                                                                                   |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `src/docker/generators/dockerfile.ts`         | `DockerfileOptions`, Dockerfile generation, and MCP proxy SDK selection                                     |
| `src/docker/generators/dockerignore.ts`       | Generated `.dockerignore` content                                                                           |
| `src/docker/generators/compose.ts`            | `ComposePaths`, Compose document types, dev service, backing services, volumes, and health-check projection |
| `src/docker/generators/supervisor.ts`         | Supervisord configuration and supervisord-specific environment quoting                                      |
| `src/docker/generators/healthchecks.ts`       | Per-process checks, monitor loops, aggregate checks, and health-check shell commands                        |
| `src/docker/generators/repositories.ts`       | Repository clone and update scripts                                                                         |
| `src/docker/generators/harnesses/opencode.ts` | OpenCode config, startup/task scripts, and telemetry plugin                                                 |
| `src/docker/generators/harnesses/pi.ts`       | Pi settings, wrapper/task scripts, and telemetry extension                                                  |
| `src/docker/generators/harnesses/codex.ts`    | Codex config, hooks, startup/task scripts, and telemetry hook                                               |
| `src/docker/generators/harnesses/claude.ts`   | Claude settings, MCP config, wrapper/task scripts, and telemetry hook                                       |
| `src/docker/generators/harnesses/shared.ts`   | Shared telemetry writer and task artifact-upload snippets used by multiple harnesses                        |
| `src/docker/generators/shell.ts`              | Shared shell quoting and duration parse/format helpers                                                      |

Keep small single-consumer helpers private to their owning module. Environment sorting may be duplicated locally if that is clearer than creating an otherwise unrelated utility module.

## Import Boundaries

The final call graph must remain:

```text
runtime/artifacts.ts
  -> docker/generators/{dockerfile,dockerignore,supervisor,healthchecks,repositories}
  -> docker/generators/harnesses/{opencode,pi,codex,claude}
  -> mcp/generator.ts

runtime/docker-compose.ts
  -> runtime/artifacts.ts
  -> docker/generators/compose.ts

runtime/docker-sandbox.ts
  -> runtime/artifacts.ts
  -> docker/generators/compose.ts

runtime/aws-ecs.ts
  -> runtime/artifacts.ts
```

Generator modules may import plan types, `runtimeLayout`, and narrowly shared generator utilities. They must not import runtime drivers, `renderCommonArtifacts`, or `writeArtifacts`.

## Implementation Steps

1. Run the focused baseline suites for Docker generators, runtime artifacts, and runtime layout. Record the existing generator snapshot state; do not update snapshots during extraction.
2. Add `shell.ts` with the existing shared shell quoting and duration behavior, including focused tests copied from current behavioral coverage.
3. Extract `dockerignore.ts`, `dockerfile.ts`, and `compose.ts`, including their private types and helpers.
4. Extract `supervisor.ts`, `healthchecks.ts`, and `repositories.ts`. Use the appropriate `runtimeLayout(...).container` fields for generated paths and verify output remains byte-for-byte identical.
5. Extract `harnesses/shared.ts` only for telemetry writer and artifact-upload behavior already shared by multiple harnesses.
6. Move OpenCode, Pi, Codex, and Claude generation one family at a time, moving each family's tests with it.
7. Update `src/runtime/artifacts.ts` to import each common generator from its final module. Do not alter manifest ordering, mode detection, `.dockerignore` preservation, MCP copying, or containment checks.
8. Update Compose-capable runtime drivers and remaining test consumers to import `generateCompose`, `generateDockerfile`, or other generators from final module paths.
9. Remove `src/docker/generator.ts` after the repository has no remaining imports of it.
10. Split snapshots by output family or retain one regression snapshot suite under `src/tests/docker/generators/`. Compare snapshots without updating them.
11. Add one representative complete-plan regression that verifies the rendered common manifest and Compose artifact, including paths, content, modes, write policies, repository scripts, health checks, MCP files, and all configured harness families.
12. Review the final imports for generator-to-runtime cycles, then run the full verification commands.

## Required Tests

- Existing generator behavior tests moved without weakening or deleting assertions.
- Existing Dockerfile, Compose, and supervisor snapshots pass unchanged.
- Focused tests for shared shell quoting and duration parsing/formatting.
- Deterministic output coverage for Dockerfile, Compose, supervisor, health checks, repositories, and each harness family.
- A representative complete-plan artifact regression verifies generated paths and textual content byte-for-byte.
- Runtime artifact tests continue to prove deterministic ordering, executable modes, `.dockerignore` preservation, path containment, complete MCP copying, and common output parity between Compose and ECS.
- Successful typecheck and build prove the final module graph has no unresolved imports; an import-boundary review proves generator modules do not depend on runtime composition or drivers.

## Acceptance Criteria

- `src/docker/generator.ts` no longer exists and no import references it.
- Every generator module owns one complete artifact or harness family; shared modules contain only helpers with multiple consumers.
- No generator source file exceeds roughly 500 lines without a documented reason.
- Existing public generator signatures remain available from their final modules.
- Generated output and artifact metadata are unchanged.
- `runtimeLayout` remains the sole source of target-scoped host and container paths.
- `src/runtime/artifacts.ts` remains the common artifact composition and writing boundary.
- Only Compose-capable drivers directly import `generateCompose`; runtime drivers do not import unrelated individual generators.
- All existing and required regression tests pass without snapshot updates.

## Non-Goals

- Redesigning generated scripts, configuration, or output paths.
- Refactoring `src/runtime/artifacts.ts`, `src/runtime/layout.ts`, or runtime drivers beyond required import changes.
- Moving or redesigning MCP plan generation or MCP runtime assets.
- Introducing a template engine.
- Renaming generator APIs as cleanup.
- Combining harnesses behind a generic abstraction that loses provider-specific behavior.
- Changing integration-test architecture beyond import updates and representative regression coverage.
